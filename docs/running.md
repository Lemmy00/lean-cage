# Running LeanCage

LeanCage already builds a program named `leancage`. Its current supported Linux
profile runs real shell/Python/native workloads in a disposable VM. The program
is assembled in [m3/Main.lean](../m3/Main.lean), uses
[LeanCageM3.API](../m3/LeanCageM3/API.lean), and invokes the
[native helper](../native/leancage_m3.c). [§AR-product.execution](architecture/AR-product.md#execution-current-path-from-policy-to-workload-and-report) maps this path;
[§FS-compatibility.interface](functional-spec/FS-compatibility.md#interface-versioned-commands) specifies its public commands.

## Build the current CLI

From the repository root, with the prerequisites in the [README](../README.md):

```sh
(cd m3 && lake build leancage)
m3/.lake/build/bin/leancage validate-policy profiles/m3/example-policy.json
```

The second command is a host-safe pure syntax/bounds check and prints
`valid policy`. It does not prepare a Linux environment. The sample policy runs
Python, creates `result.json` with `{"answer": 42}` in its private workspace and
requests regular-file export; its exact limits and runtime digest are in
[example-policy.json](../profiles/m3/example-policy.json).

The controller's `check` and `run` require the designated VM, prepared runtime,
input store and helper. Building the CLI alone does not install those dependencies
or enable execution on the shared host.

## Run real workloads in the existing VM

For the supported Ubuntu 24.04 x86-64 bootstrap, first prepare project-local tools,
the frozen runtime and kernel if this checkout has not already been prepared:

```sh
python3 scripts/run_m3_vm.py --prepare
```

Then run the existing executable acceptance path:

```sh
python3 scripts/run_m3_vm.py --development
```

This builds the controller/helper/image, boots the disposable VM, executes the
60 workload cases, three CLI API checks and six death/cancellation boundaries,
then shuts it down. It includes useful shell/Python execution, filesystem/output
behavior, denied effects, limits and descendant cleanup. Development mode keeps
its transcript under `.tools/m3vm/development-transcript.log` and does not replace
the accepted evidence. It is a replay using cached tools, not a new assurance
record or a production deployment. [§AR-workspace.acceptance](architecture/AR-workspace.md#acceptance-coverage-and-handoff-gate) defines acceptance.

The current VM starts an automated harness; it is not an interactive shell. The
three commands that harness invokes inside it are:

```sh
/leancage check /api-policy.json
/leancage run /api-policy.json
/leancage report RUN_ID
```

These are VM paths, not host commands. `/api-policy.json` is generated by
[the image builder](../scripts/run_m3_vm.py); it tests Python with frozen input
and stdin. `RUN_ID` is the actual ID allocated by `run`. `check` prepares and
tears down without guest entry. `run` executes and stores its JSON result under
`/m3-results/RUN_ID/report.json`; `report` retrieves the published result. Captured
guest output and workspace export are separate artifacts under that run directory,
as specified in [§FS-workspace.results](functional-spec/FS-workspace.md#results-entry-cancellation-and-bounded-transport) and [§FS-workspace.filesystem](functional-spec/FS-workspace.md#filesystem-snapshots-aliases-and-lifetime).

For the full proof/build gate, use:

```sh
./scripts/check.sh
```

That checks proofs, native compilation, archived VM records and pure tests. It
does not execute guest workloads on the host. Normal VM replay without
`--development` updates accepted evidence and therefore belongs to the reviewed
workflow in [the development guide](development.md).

## Next product delivery

The current host entry point runs fixed acceptance workloads. The next assignment
adds a caller-policy VM workflow, returned captures/export, reusable library and
one root build bundle under [§FS-linux-product.operation](functional-spec/FS-linux-product.md#operation-run-a-callers-workload-through-one-supported-interface).
It also consolidates maintained product code into functional components.

The [revised roadmap](roadmap.md) separates this M4 delivery from M5 application
verification and M6 platform/confidentiality improvements. M7 supports releases
whose declared proof and trust profile matches their evidence. The commands above
remain the current executable interface until the product workflow is implemented.
